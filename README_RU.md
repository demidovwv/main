# Авито → Telegram: быстрый поиск «Железного пламени»

Версия 1.6, 02.11.2026. Приоритетный поиск «Железное пламя» раз в 45 секунд, остальные запросы по одному в промежутках. Ссылка на новое объявление уходит в Telegram сразу. Это браузерный мониторинг выдачи, не подписка на внутренние события Авито.

## Версия 1.6: стабильный опрос раз в 30–60 секунд

Восемь поисков нельзя открывать каждые 30–60 секунд все сразу. Одна страница занимает несколько секунд, и такая очередь уже приводила к HTTP 429. Версия 1.6 делит нагрузку так:

- «Железное пламя» — приоритет, интервал 45 секунд (допустимый диапазон в конфиге 30–60; меньше 30 код поднимает до 30). Новая карточка сразу ставится в очередь Telegram, ссылка стоит в начале сообщения.
- Остальные семь запросов — интервал 300 секунд и не больше одного за промежуток между приоритетными проверками. Первые заходы разнесены, а не выстреливают пачкой при старте.
- Между началами переходов не меньше 8 секунд. В поставленном `config.json` описания выключены (`fetch_descriptions: false`), а «возможные варианты» не рассылаются (`notify_candidates: false`): после HTTP 429 лишние страницы и шумные сообщения не нужны. Книга в заголовке или видимом фрагменте по-прежнему уходит со ссылкой. Описания можно вернуть, когда обычный браузер снова стабильно открывает выдачу.
- При запуске монитора браузер открывается сам. Старая ручная пауза в базе больше не держит его выключенным. Если Авито отвечает 429 или страница не загружается, интервал «Железного пламени» растёт на 15 секунд, максимум до 120, и обновление продолжается без `--resume`. Капча, HTTP 403 и 439 по-прежнему останавливают заходы до ручной проверки. История объявлений в `data` не сбрасывается.

Сервер в другой стране сам по себе Авито не открывает. Если на машине поднят VPN на весь сервер, браузер идёт через него и `AVITO_PROXY_SERVER` можно оставить пустым. Если российский выход — это только локальный порт SOCKS/HTTP, его нужно записать в `.env`. Адрес `127.0.0.1` внутри Docker — это контейнер, не соседний VPN-процесс. Пароль прокси в журнал не пишется.

Проверка версии: `python avito_watch.py --version`. После замены файла и `config.json` папку `data` и `.env` не удалять.

## Версия 1.5: какой запрос получил 429, описания и паузы в журнале

По присланной выдержке нельзя установить, какой запрос получил 429 в 15:48:24: версия 1.4 не сохраняла этот контекст. Три ошибки описания одной карточки в 15:41, 15:42 и 15:44 соответствуют прежнему пределу в три попытки, а не доказывают бесконечные повторы. Однако после постоянной ошибки разметки такие частые повторы не улучшали результат.

Версия 1.5 добавляет:

- Строку `Авито START` с типом (поиск/описание), целью, публичным URL и количеством начатых навигаций скрипта за последние 60 секунд; строку `Авито END` с длительностью. Старт выводится непосредственно перед фактической навигацией, после ожидания общей очереди. Это позволяет видеть работу в прежних «тихих» промежутках. Счётчик навигаций **не включает** все загрузки ресурсов/фоновые HTTP-запросы самого браузера и не равен счётчику ограничения на стороне Авито.
- Тип и URL отказавшего запроса в общей паузе, Telegram и сохранённом `--status`. Это показывает, **какой запрос получил ответ**, а не доказывает единственную причину ограничения. Из старых сохранённых пауз URL восстановить нельзя.
- Параметры, похожие на токены/сессии и длинный `context`, исключаются из диагностического URL. Пароли прокси и токен Telegram в этот журнал не выводятся.
- При нераспознанном описании, обычном HTTP 4xx (кроме обрабатываемых глобально 403/429/439), проверка этой карточки завершается сразу, без повторов. HTTP 408 и 5xx считаются временной ошибкой.
- При таймауте/сетевой ошибке — максимум две попытки всего, повтор не раньше чем через 15 минут. Счётчик и срок сохраняются в SQLite. Старые незавершённые задания, у которых уже исчерпаны две попытки, завершаются без нового открытия. Успешно завершённые задания заново не запускаются.
- Между завершением одной проверки описания и следующей — минимум 30 секунд, вне общей блокировки навигаций. Это снижает вторичную нагрузку, но не гарантирует отсутствие ограничений.
- В строке ошибки описания теперь указаны причина, попытка `1/2` или `2/2`, URL и решение: «повтор не раньше …» или «проверка завершена, повторов не будет». Сообщение об объявлении получает явную пометку о завершении попыток.

Для следующего контролируемого испытания после уже полученного 429 можно **временно отключить все описания**. Остановите цикл `run.sh` и Python, замените только `avito_watch.py`, оставьте свои `.env`, `data`, профиль и конфиг с 45 секундами. Добавьте в существующий JSON-объект конфигурации:

```json
"fetch_descriptions": false
```

Это строка внутри существующего JSON-объекта, не полный файл; соблюдите запятые между параметрами. Очередь описаний сохраняется, но вкладка для них не создаётся и навигации не выполняются. Поиски и отправка найденного продолжают работать. При `notify_candidates=false` подтверждение берётся только из заголовка/видимого фрагмента: книга, упомянутая только в полном описании или видимая только на фото, может быть пропущена. Это временное уменьшение охвата ради изоляции вторичной нагрузки; отсутствие 429 в коротком испытании ещё не доказывает стабильность.

Сохранённая общая пауза остаётся в силе. Не удаляйте `data` и не вызывайте принудительные проверки в цикле. После окончания срока допустима одна предусмотренная проверка с тем же рабочим браузером/профилем. `--resume` нужен только при ручной остановке после ручной проверки; он не сокращает Retry-After.

Когда доступ подтверждён и нужен возврат проверки описаний, измените `fetch_descriptions` на `true`: отложенная очередь продолжится с сохранёнными счётчиками. Параметры по умолчанию:

| Параметр | Значение | Поведение |
|---|---:|---|
| `fetch_descriptions` | true | Выполнять очередь описаний; false полностью останавливает её навигации |
| `detail_max_attempts` | 2 | Общее число попыток; допускается 1–2 |
| `detail_retry_seconds` | 900 | Пауза перед повтором временной ошибки, минимум 900 с |
| `detail_min_gap_seconds` | 30 | Пауза после завершения одной попытки описания, минимум 30 с |

Новые параметры имеют эти значения даже при обновлении только Python-файла со старым конфигом. Внешний профиль, окно, прокси, интервалы поисков и история объявлений не сбрасываются. Реальный журнал компьютера агента находится у агента; автор этого комплекта проверил код и присланную выдержку, а не содержимое удалённого `/workspace/avito-iron-flame/watcher/watch.log`.

## Версия 1.4: число карточек меняется при загрузке страницы

Версия 1.3 начинала читать HTML сразу после появления первой карточки. При динамической загрузке это могло дать только часть списка. Наблюдение «47 → 32 → 19» поэтому само по себе не доказывает мягкое ограничение: в этих числах смешиваются момент чтения DOM, реальное содержание выдачи и другие возможные причины. Число 50 в журнале — число разобранных карточек первой загруженной страницы, а не обязательно общий счётчик найденных объявлений в заголовке Авито.

В версии 1.4 после открытия поиска:

- Первый распознанный набор карточек сразу обрабатывается и ставится в очередь уведомлений, без ожидания остальных.
- Затем программа читает DOM той же страницы примерно каждые 0,5 секунды. При появлении следующих карточек они сразу обрабатываются тоже. Повторные номера не создают новых сообщений.
- Чтение завершается, когда список номеров не меняется 1,5 секунды, либо через максимум 8 секунд. Это ограниченное ожидание, а не доказательство полной выдачи.
- Во время такого чтения не выполняются дополнительные `goto`, обновления страницы или прокрутки. Частота поисковых навигаций в конфиге не меняется. Страница может сама продолжать обычную загрузку ресурсов.
- Сохраняются все уникальные номера, увиденные в рамках одного чтения. В журнале теперь есть строка `DOM «...»: сначала 5, в конце 50, уникальных за чтение 50; список стабилен 1.5 с` либо пометка о достижении предела ожидания.
- На самом первом обходе все эти порции попадают в начальную базу без рассылки. Уже существующая база не сбрасывается и не заполняется заново после обновления.

Обновление рабочего монитора: остановить `run.sh` и Python; заменить только `avito_watch.py`; оставить свои `.env`, `config.json`, браузерный профиль и `data`; запустить тем же способом в той же графической сессии. Настройки 45 секунд и `notify_candidates=false` менять не требуется. Проверьте версию командой `.venv/bin/python avito_watch.py --version`.

После обновления посмотрите несколько обычных циклов, не добавляя частых ручных обновлений. Рост `сначала 5 → в конце 50` поддержит гипотезу о неполной начальной загрузке. Стабильные 5 карточек в конце означают только то, что за время наблюдения распознано 5: это не доказывает ни ограничение, ни полноту выдачи. Для дальнейшей диагностики нужно сравнить фактический вид той же страницы с разобранными карточками. Само по себе уменьшение числа не включает общую паузу; её вызывают реальные ответы 429/439/403 или проверка доступа.

## Компьютер агента в Атланте + российский Happ: тест версии 1.3

Физическое расположение компьютера само по себе не определяет сетевой маршрут браузера: важно, чтобы именно процесс браузера использовал заданный SOCKS5-прокси. В вашем случае обычный поиск уже открылся через Happ, поэтому есть смысл сравнить скрипт в том же браузере и выделенном профиле, с окном. Это проверка различий окружения, а не гарантия отсутствия последующих ограничений.

1. Остановите монитор и цикл `run.sh`. Пока обычный браузер открыт, проверьте `chrome://version`: строку исполняемого файла и «Путь к профилю». Если путь заканчивается на `Default` или `Profile 1`, для `BROWSER_PROFILE_DIR` нужен его **родительский User Data Directory**. Уточните, что `/home/box/chrome-profile/avito-proxy` — именно этот корень и отдельный профиль Авито, а не основной повседневный профиль пользователя.
2. Закройте все окна и фоновые процессы браузера, использующие этот User Data Directory. Другие профили не нужно закрывать. Не удаляйте `SingletonLock` и подобные файлы для принудительного открытия. Перед первым использованием существующего выделенного профиля полезно сделать его локальную резервную копию после закрытия браузера; профиль с cookies не нужно никуда загружать.
3. Замените **только `avito_watch.py`** на версию 1.3. Свои `.env`, `data` и `config.json` сохраните: настройки 45 секунд и `notify_candidates=false` могут остаться.
4. Если обычный браузер — установленный **Google Chrome**, добавьте/исправьте в `.env`:

```dotenv
AVITO_PROXY_SERVER=socks5://127.0.0.1:10808
BROWSER_PROFILE_DIR=/home/box/chrome-profile/avito-proxy
BROWSER_CHANNEL=chrome
BROWSER_HEADLESS=false
BROWSER_EXECUTABLE_PATH=
```

Если обычный браузер — Chromium или нестандартная сборка Chrome, не угадывайте `chrome`: оставьте `BROWSER_CHANNEL` пустым и укажите в `BROWSER_EXECUTABLE_PATH` точный существующий путь из `chrome://version` без аргументов запуска. Одновременно задавать канал и исполняемый файл нельзя. Собственный путь браузера поддерживается Playwright с ограничениями совместимости; результат нужно проверить.

5. Запускайте тест **тем же пользователем, из терминала той же графической сессии**, где работал обычный браузер. В Linux должна быть доступна корректная переменная `DISPLAY` и права к этой сессии. Значение `DISPLAY` не нужно угадывать или заменять на `:0` вслепую. Через обычный SSH без доступа к рабочему столу окно не появится. Стандартный Docker-контейнер из комплекта для этого теста не подходит: внутри него нет GUI, браузера Chrome и этого профиля, а `127.0.0.1` означает контейнер.

Поскольку ручная проверка уже выполнена, после окончания сохранённой паузы разрешите следующую одиночную попытку и проверьте первый поиск:

```bash
.venv/bin/python avito_watch.py --resume
.venv/bin/python avito_watch.py --probe --headed
```

`--resume` не сокращает Retry-After и не запускает поиск. Если срок ещё не наступил, тест не откроет браузер. `--probe` не рассылает объявления и не заполняет начальную базу. В журнале перед запуском браузера должны появиться **выбранный браузер, `/home/box/chrome-profile/avito-proxy` и `окно: да`**. При неверной папке скрипт не создаёт незаметно новую пустую сессию; при занятом профиле/отсутствии GUI выводит пояснение.

Результат `OK` и реальные названия карточек подтвердят, что этот запуск получил распознанную выдачу. Только после этого можно один раз запустить обычный монитор в той же сессии:

```bash
.venv/bin/python avito_watch.py
```

`BROWSER_HEADLESS=false` сохранит окно и при запуске без `--headed`. После проверки можно вернуться к своей обёртке `run.sh`, убедившись, что она запускается в том же окружении с графической сессией. Сохраняйте оба потока вывода: `.venv/bin/python avito_watch.py >> watch.log 2>&1`. Не запускайте одновременно ручной браузер с тем же профилем и монитор.

Если и этот одиночный тест получит 439/429, доступ автоматизированного запуска по-прежнему не подтверждён. Постоянный поиск не запускайте, передайте фактический вывод теста. Существующий профиль и открытое окно не делают автоматизацию полностью идентичной ручному браузеру.

Выбор профиля можно также передать разово через `--profile-dir /абсолютный/существующий/каталог`; он имеет приоритет над `.env`. Папка базы `data` от этого не меняется. Внешний профиль нельзя указывать вместо базы `WATCH_STATE_DIR`: это разные настройки.

## Что изменено в версии 1.2

- HTTP 439 теперь сразу останавливает все автоматические навигации и требует ручной проверки, как 403. Это нестандартный HTTP-код; по нему программа **не делает вывод, что заблокирован именно IP VPN**. После 439 другие запросы не перебираются.
- Пауза, созданная диагностикой `--probe`, сохраняется, но сама диагностика по-прежнему ничего не отправляет в Telegram. При последующем запуске постоянного поиска версия 1.2 добавляет одно уведомление об этой сохранённой паузе каждому настроенному получателю. Перезапуски не создают повторов того же статуса.
- Если обычный постоянный поиск получил 429, предупреждение должно появиться в очереди Telegram. Если оно не пришло, проверьте реальную доставку отдельно: `py avito_watch.py --test-telegram`. Эта команда не обращается к Авито. Команда `--status` тоже не обращается к Авито и показывает сохранённую паузу.
- Состояние сайта, ручной проверки и бота нужно проверять по журналу и фактическим ответам, а не только по пересказу агента. Даже успешный тест Telegram не подтверждает доступ к Авито.

Обновление: остановите старую копию, замените `avito_watch.py`, сохраните `.env` и `data`. Профиль частоты и `config.json` из версии 1.1 не меняются. При переходе с версии 1 замените также конфиг. Для проверки версии: `py avito_watch.py --version`. На Docker требуется пересборка `docker compose build` после остановки старого контейнера; не удаляйте том данных.

После окончания срока паузы проверьте один и тот же поиск **один раз** в обычном браузере и в диагностике, с тем же подключением/VPN. Если обычный браузер тоже ограничен, доступ с этого подключения не подтверждён; если он работает, а автоматизированный нет, причина может быть в сессии, способе обращения или других признаках. Это диагностические предположения, не доказательство конкретной причины. Смена сервера Happ сама по себе не подтверждает и не исправляет работу монитора.

## Что уже сделано и что ещё нужно проверить

Код и автономные тесты подготовлены. Проверяются обработка карточек на тестовой HTML-разметке, фильтр книги, база, два получателя, восстановление очереди, обновление сообщения и ошибки Telegram. Реальная выдача Авито с вашего подключения и реальная отправка вашим ботом здесь не проверены. Сначала выполните `--probe` и `--test-telegram` ниже. До успешной проверки это пробная версия, а не подтверждённый работающий монитор.

**Каждое впервые обнаруженное объявление отправляется отдельно сразу после обнаружения.** Однако момент обнаружения зависит от появления в выдаче и частоты её проверки. После фактически полученных HTTP 429 профиль частоты изменён: основной запрос «Железное пламя» — раз в 20 секунд, остальные семь — раз в 120 секунд. Это осторожные стартовые настройки для испытания, а не известный разрешённый лимит Авито. Интервал может быть больше из-за загрузки страниц и очереди. «Мгновенно с момента публикации» этот способ не гарантирует.

## Если уже пришли сообщения HTTP 429: обновление с версии 1

HTTP 429 означает ограничение частоты запросов, а не отсутствие книг. Точная причина/область ограничения (IP, сессия, другие признаки) из одного кода ответа неизвестна. В версии 1 были ошибки: восемь слишком частых поисков и отдельные паузы, пока другие поиски продолжали обращения. Версия 1.1 снижает нагрузку и вводит один общий предохранитель. Это **не средство снятия ограничения или обхода проверки**.

1. Остановите старую копию: Ctrl+C или `docker compose down`.
2. Приостановите также другие автоматические проверки Авито с этого подключения, включая прежнего агента. Не запускайте два монитора параллельно.
3. Замените `avito_watch.py`, `config.json` и инструкцию файлами из обновлённого архива. **Сохраните свои `.env` и папку `data` / Docker-том:** не удаляйте историю и профиль. Если у вас были собственные поисковые ссылки, перенесите их в новый конфиг, сохранив увеличенные интервалы. Если обновить только скрипт со старым конфигом, он принудительно увеличит интервалы меньше 20 с до 20 с, задаст одну загрузку и общий промежуток минимум 5 с; лучше использовать новый конфиг.
4. Не проверяйте выдачу непрерывно. Сделайте паузу, например 30–60 минут, если сервер не указал более долгий срок. Это пример паузы для диагностики, **не обещанный срок разблокировки**. Если известен `Retry-After`, дождитесь как минимум его окончания.
5. Затем **один раз** выполните:

```powershell
py avito_watch.py --probe --headed
```

Команда проверяет только основной поиск, ничего не рассылает и не запоминает объявления как просмотренные. Состояние ограничения, если оно обнаружено, сохраняется в базе. Если опять 429 — остальные поиски не открываются. Дальше не уменьшайте интервалы и не перезапускайте программу в цикле: посмотрите состояние:

```powershell
py avito_watch.py --status
```

При первом 429 все новые навигации Авито (поиски, описания, диагностические проверки) приостанавливаются как минимум на 15 минут или на больший `Retry-After`. Пауза сохраняется после перезапуска. По окончании допускается одна проверка поиска, а описания ждут. Если снова 429, либо показаны 403/439/капча, программа сохраняет ручную остановку и не пытается другие запросы. В обычном браузере с **тем же подключением** проверьте доступ один раз; при необходимости выполните обычную ручную проверку сайта. Работу текущего монитора сначала остановите.

Только после ручной проверки разрешите следующую диагностическую попытку:

```powershell
py avito_watch.py --resume
py avito_watch.py --probe --headed
```

`--resume` не делает запросов, не запускает монитор и **не сокращает срок паузы / Retry-After**. Если пауза ещё не закончилась, `--probe` не откроет браузер и покажет срок. При успешном распознавании выдачи (`OK`) можно запустить монитор. Новая версия создаёт одно общее сообщение о паузе, а не сообщение на каждый поисковый запрос; при повторном ограничении возможен ещё один общий статус о ручной остановке. Восстановление подтверждается отдельным общим статусом.

Если даже первая одиночная проверка продолжает получать 429, доступ из этого браузера/подключения не подтверждён. Менять количество секунд в коде недостаточно. Быстрый самостоятельный монитор пока нельзя считать рабочим. Альтернатива для проверки — штатные уведомления или сторонний мониторинг с испытанием реальной скорости и полноты, без обещания мгновенности.

## Как работает

- Постоянный Chromium через Playwright, отдельная папка профиля. Никаких методов скрытия автоматизации или автоматического решения капчи нет.
- Россия целиком, раздел книг, в автоматически сформированных ссылках задано `s=104` (ожидается сортировка по новизне). При первом `--probe --headed` проверьте в браузере, что раздел, регион и сортировка действительно выбраны правильно. Более надёжно скопировать рабочие ссылки из вашего браузера в `config.json`.
- Все восемь запросов сохранены: «Железное пламя», «Четвёртое крыло», «Эмпирей», «Ребекка Яррос», «Яррос», «4 крыло», «Железное пламя обрез», «Ребекка Ярос». Любой можно отключить или заменить ссылкой.
- Новый подходящий номер объявления сразу ставится в постоянную очередь. Отдельный отправитель проверяет очередь примерно каждые 0,15 секунды. Он не ждёт остальных поисков или анализа описания.
- Одно объявление — одно сообщение каждому указанному получателю. Два объявления — два отдельных сообщения. Во время обычной работы сообщения могут редактироваться после загрузки описания.
- Не ждём анализа фотографий: в этой версии **нет ИИ/OCR и нет автоматического определения специальной обложки/обреза**. Их нужно проверить по ссылке. Это прямо указано в уведомлении.
- Если название или видимый фрагмент содержит «Железное пламя», приходит уведомление с пометкой, что книга указана в тексте. Это не подтверждение нужного издания или доступности товара.
- Если виден связанный цикл, автор или общий набор книг, приходит **«Возможный вариант — состав нужно проверить»**. Это намеренно предварительное уведомление ради скорости: иногда нужной книги там не окажется.
- Затем независимо загружается полное описание. При подтверждении или отказе обновляется то же сообщение. При нераспознанном описании повторы завершаются сразу, при временной ошибке — после максимум двух попыток с паузой не менее 15 минут; в сообщении появится просьба проверить карточку вручную. Фото автоматически не анализируются.
- «Куплю/ищу», «Рыцарь и мотылёк» без целевой книги, явное «Железное пламя продано/без Железного пламени» отбрасываются. Проверка текста эвристическая: сложные формулировки продавца могут быть поняты неверно.
- Ценового лимита нет, отдельные книги и наборы допускаются. Наборы показываются исходным названием и фрагментом текста продавца, без выдуманного состава.
- SQLite хранит уже замеченные номера и отправку каждому получателю отдельно. При штатном перезапуске старое не отправляется повторно; неотправленная очередь сохраняется. Редкий дубль возможен при обрыве в момент, когда Telegram уже принял сообщение, а программа ещё не успела записать ответ. Абсолютную «ровно одну доставку» Bot API не гарантирует.
- HTTP 429/403/439 и проверка доступа останавливают обращения глобально, включая описания. Неизвестная разметка и обычные ошибки загрузки обрабатываются отдельно как ошибки конкретного поиска, а не как «0 новых». Сбой самого Telegram может помешать и служебной доставке; смотрите журнал.

## Запуск на Windows

Нужен Python 3.11 или новее. Распакуйте архив, например в `C:\avito_book_watch`, и откройте терминал внутри этой папки.

### 1. Установить зависимости и браузер

```powershell
py -m pip install -r requirements.txt
py -m playwright install chromium
```

### 2. Проверить, что Авито доступен

Включите своё рабочее подключение/VPN, если через него Авито открывается.

```powershell
py avito_watch.py --probe --headed
```

Тест проверяет только первый поиск, ничего не отправляет в Telegram и не создаёт начальную базу объявлений; сохраняется лишь состояние ограничения доступа. Он печатает `OK`, число карточек и примеры названий либо `ОШИБКА`. Если нужен вход, а общей паузы/ограничения нет, используйте:

```powershell
py avito_watch.py --login
```

В открытом браузере вручную откройте нужный поиск, при необходимости войдите или пройдите обычную проверку. Вернитесь в терминал и нажмите Enter. Профиль сохранится в `data/browser-profile`. После необходимой паузы выполните один `--probe --headed`. При 429/403/439 действуйте по разделу восстановления выше. Не запускайте две копии с одной папкой данных.

Программа не обязана работать через системный прокси Happ автоматически. Если Happ работает как VPN/TUN, маршрут может применяться ко всему браузеру; если это отдельный прокси, задайте его точный адрес в `.env`. Адрес нужно взять из ваших настроек, а не угадывать.

### 3. Подключить Telegram

```powershell
Copy-Item .env.example .env
notepad .env
```

Заполните файл локально:

```dotenv
TELEGRAM_BOT_TOKEN=ТОКЕН_ВАШЕГО_БОТА
TELEGRAM_CHAT_IDS=ПЕРВЫЙ_ЧИСЛОВОЙ_CHAT_ID,ВТОРОЙ_ЧИСЛОВОЙ_CHAT_ID
```

Оба получателя должны открыть бота и нажать «Старт». Можно использовать существующего бота, если известны токен и chat_id. Но **для теста удобнее отдельный бот** через [@BotFather](https://t.me/BotFather), чтобы не мешать текущему агенту.

Если chat_id неизвестны, сначала заполните только токен, отправьте `/start` боту с обоих аккаунтов и выполните:

```powershell
py avito_watch.py --get-chat-ids
```

Команда показывает числовые chat_id по входящим сообщениям. **Не применяйте её к боту с работающим обработчиком входящих сообщений/webhook:** сообщения может забирать другой процесс, а getUpdates при webhook не работает. Команда не удаляет webhook и ничего не перенастраивает. Для такого бота возьмите известные chat_id у текущего агента.

После заполнения chat_id:

```powershell
py avito_watch.py --test-telegram
```

Должно прийти тестовое сообщение обоим получателям. Токен не нужно отправлять в чат и нельзя публиковать.

### 4. Запустить постоянный поиск

```powershell
py avito_watch.py --headed
```

Первый успешный обход **каждого поиска** запоминает текущие видимые объявления без рассылки. Это начальная база, чтобы не получить сразу все старые варианты. Затем отправляются впервые замеченные номера. Во время начального обхода уведомления могут ещё не приходить; небольшое окно начального заполнения неизбежно. Нормально останавливать программу через Ctrl+C.

Если вы хотите разово получить также текущие объявления из выдачи, на первом запуске вместо предыдущей команды используйте:

```powershell
py avito_watch.py --headed --first-run notify
```

Это может отправить много объявлений! Режим нужен только если вы намеренно хотите такой первый обход. Не удаляйте папку `data`: иначе история потеряется и база будет создаваться заново.

Чтобы импортировать уже просмотренные 130 объявлений, создайте `old_seen.txt`: по одной ссылке Авито или одному номеру на строку. На запуске укажите:

```powershell
py avito_watch.py --headed --seed-ids old_seen.txt
```

Поиск базы на вашем компьютере автоматически не выполняется; список текущего агента нужно выгрузить явно. Импорт ничего не отправляет.

## Конфигурация поиска

Пример записи в массиве `searches`:

```json
{"query": "Железное пламя", "url": "СКОПИРОВАННАЯ_HTTPS_ССЫЛКА_ПОИСКА_АВИТО", "interval_seconds": 120, "enabled": true}
```

`query` здесь — подпись для сообщений, `url` — точная ссылка с вашими фильтрами. Если `url` отсутствует, ссылка создаётся автоматически. Работоспособность автоматически созданных ссылок нужно проверить, особенно у запросов, которые сейчас у агента дают пустые страницы. При реальном «ничего не найдено» поиск считается пустым; при нераспознанной странице выводится ошибка. Не отключайте проблемный запрос молча, считая его перекрытым другими.

Общие параметры:

| Параметр | Значение по умолчанию | Смысл |
|---|---:|---|
| `interval_seconds` | 300 | Интервал остальных запросов. Приоритетный запрос задаёт свой, сейчас 45 с |
| `navigation_gap_seconds` | 8 | Минимальная пауза между началами навигаций всех поисков/описаний |
| `max_secondary_per_cycle` | 1 | Сколько остальных запросов можно открыть между проверками приоритетного. Допустимо 0–2 |
| `search_concurrency` | 1 | В версии 1.1 навигации Авито выполняются строго по одной |
| `cooldown_seconds` | 900 | Минимальная общая пауза при 429, секунд; Retry-After может её увеличить |
| `notify_candidates` | true | Сразу уведомлять о потенциальных наборах/циклах без подтверждения целевой книги |

Чтобы получать только текстовые подтверждения, поставьте `notify_candidates: false`: неоднозначные варианты будут ждать загрузки описания, а фото без подтверждения текстом могут быть пропущены. Это снижает шум, но противоречит приоритету максимальной скорости/охвата. По умолчанию включён быстрый режим.

В этой версии интервалы меньше 30 с, общий промежуток меньше 8 с и параллельные навигации принудительно ограничены. Это защита от повторения нагрузки версии 1, а не установленный лимит Авито. Снижение частоты не гарантирует доступ: даже одиночная проверка может получить ограничение. Текстовое уведомление по-прежнему отправляется немедленно после обнаружения, без накопления подборки.

После успешного одиночного теста для разовой проверки всех запросов можно использовать `--probe --probe-all --headed`. При первом ограничении этот обход прекращается. Не запускайте такую диагностику постоянно.

Проверяется только первая загруженная страница каждой выдачи. При большом потоке между проверками возможен пропуск. Впервые замеченный номер не обязательно только что опубликован: старое объявление может подняться в выдаче. Поэтому сообщение честно показывает время обнаружения, а не выдуманное время публикации. Правки уже замеченных объявлений и новые фото в этой версии не отслеживаются.

## На сервере: Docker Compose

Сначала убедитесь, что монитор работает на выбранном подключении. Начальный ориентир для VPS с браузером: 2 vCPU, 4 ГБ RAM, Ubuntu/Debian, Docker и Compose. Это оценка для испытания, а не гарантированный минимум. Доступ к Авито с IP сервера надо проверить до долгой аренды: российский IP и VPS сами по себе не гарантируют доступ. Happ с домашнего компьютера на сервер не переносится автоматически.

Скопируйте папку на сервер. Создайте и заполните `.env` как выше. Если серверу нужен прокси для Авито, задайте:

```dotenv
AVITO_PROXY_SERVER=http://АДРЕС:ПОРТ
AVITO_PROXY_USERNAME=
AVITO_PROXY_PASSWORD=
```

Не ставьте адрес `127.0.0.1` из примера Windows без проверки: **в контейнере это сам контейнер, а не домашний компьютер или хост сервера**. Не публикуйте прокси/браузер наружу.

```bash
docker compose build
docker compose run --rm watcher python avito_watch.py --probe
docker compose run --rm watcher python avito_watch.py --test-telegram
```

После обновления кода на сервере заново выполните `docker compose build`. Состояние/история в прежнем именованном томе сохраняются. `--status` и `--resume` доступны через `docker compose run --rm watcher python avito_watch.py --status` (или `--resume`); сначала остановите основной контейнер, иначе сработает защита от двух копий.

Если обе проверки успешны:

```bash
docker compose up -d
docker compose logs -f --tail=100
```

После выхода из SSH монитор продолжит работать; после перезапуска Docker контейнер поднимется автоматически. Данные хранятся в именованном томе `watcher_data`. Чтобы остановить:

```bash
docker compose down
```

Не используйте `docker compose down -v`, если хотите сохранить историю. После изменения `.env` или `config.json` выполните `docker compose up -d --build --force-recreate`.

В контейнере нет графического интерфейса. Если `--probe` показывает блокировку/нужен ручной вход, не запускайте бесконечный монитор вслепую. Возможные следующие шаги: запуск напрямую на Linux с графической сессией/защищённым удалённым рабочим столом и `--login`, либо другой источник уведомлений. Удалённый рабочий стол в этот комплект не входит. Перенос профиля с Windows на Linux может не сохранить авторизацию, поэтому на него нельзя полагаться.

Текущее решение не требует публичного порта на сервере: оно само читает Авито и отправляет запросы Telegram. Не забудьте отключить старый агент или использовать отдельного бота/получателей, когда убедитесь, что новый монитор подходит, иначе два независимых монитора могут прислать одно объявление каждый.

## Проверка кода

```bash
python -m unittest discover -s tests -v
```

Автономные тесты проверяют также общий стоп после первого 429, Retry-After, запрет другим запросам и описаниям, сохранение паузы, ручной режим и проверки доступа при HTTP 200. Они не отправляют сообщения и не обращаются к Авито. HTML-примеры синтетические, а не текущая сохранённая выдача сайта; только `--probe` с реальным подключением покажет совместимость с текущей разметкой.

Если реальная страница не распознаётся, пришлите текст ошибки `--probe` и названия/ссылки поисков. Токен и пароли не присылайте. Сначала нужно исправить доступ/разметку, затем включать постоянную рассылку.
